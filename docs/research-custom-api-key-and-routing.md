# Custom API keys and usage-first routing research

## Findings

- The repository already accepts API-key credentials for built-in providers and named OpenAI-compatible providers. `OpenAICompatibility` contains a `base-url`, `api-key-entries`, and model definitions ([configuration types](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/internal/config/config_types.go), [configuration example](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/config.example.yaml)).
- The config synthesizer turns each configured OpenAI-compatible key into an API-key auth entry and carries the configured base URL into runtime attributes ([synthesizer](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/internal/watcher/synthesizer/config.go)). The executor sends the key as Bearer auth and appends its standard operation route to the configured base URL ([executor](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/internal/runtime/executor/openai_compat_executor.go)). A custom path prefix such as `https://gateway.example.com/custom/v1` is therefore supported; an arbitrary replacement for `/chat/completions` or `/responses` is not exposed as configuration. The standard operations have distinct routes in the [Chat Completions](https://platform.openai.com/docs/api-reference/chat/create) and [Responses](https://platform.openai.com/docs/api-reference/responses/create) APIs.
- The existing `fill-first` selector already prefers the first ready credential and, for mixed-provider requests, the first provider in route order. Quota and cooldown state removes unavailable credentials from selection, allowing existing retry logic to advance to another account/provider ([selector](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/sdk/cliproxy/auth/selector.go), [scheduler](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/sdk/cliproxy/auth/scheduler.go), [execution/retry flow](https://github.com/jasonb194/CLIProxyAPI/blob/d7914afd/sdk/cliproxy/auth/conductor_execution.go)). The application currently defaults to round-robin, so making fill-first the default is the narrowest change for automatic usage-first routing; explicit round-robin and weighted round-robin can remain available.

## Design direction

Document and test the supported custom base URL path-prefix configuration. Make fill-first the default for newly configured and unconfigured runtime routing, while preserving explicit strategy settings and the existing cooldown/retry implementation. Add an arbitrary endpoint-route field only if the desired integration requires a nonstandard operation path; that would need a clear rule for which operations and protocols it controls.
